# textheat browser extension

Manifest V3 companion for Chromium browsers (Chrome, Edge, Brave). It bundles the existing public `textheat` package; there is no copied analyzer, second lexicon, remote service, or native model in the extension.

Minimum declared browser version: **Chrome/Chromium 120**. Build-generated PNG icons cover 16/32/48/128 pixels; package and manifest versions are checked for consistency. Compatibility on other Chromium distributions must still be tested rather than assumed from their name.

## Shared expanded analyzer

The shared English dictionary has **5,981 unique entries: 1,850 words and 4,131 phrases**, with a derived maximum of **12 words** per phrase. The latest review layer adds **339 individually authored keys: 213 words and 126 phrases**, with **no template generation in that layer**. Earlier domain layers include constrained compatible review-template combinations—not an external corpus, imported lexicon, or training dataset. More entries and combinations do not imply measured accuracy. The frozen `lexiconStats` object reports `{ entries: 5981, words: 1850, phrases: 4131, maxPhraseWords: 12 }` through implemented named exports from the root, core, and browser entry points; see [the statistics contract](API.md#lexicon-statistics). Extension settings do not change those counts or scores.

The extension uses the same analyzer precedence: **curated bounded noun frames before individual lexical terms**, with **existing exact phrases at the starting token retaining precedence**; otherwise longest lexical matches win. A recognized negative noun frame consumes the descriptors and head together, not a subjective adjective painted independently green inside negative problems. A listed negated observation prefix + **see/find/notice/detect/encounter/experience/have** + optional **any/a/no** + **zero to three explicitly listed descriptors** + a listed singular/plural negative head consumes one full span. Heads are **problem/problems, issue/issues, bug/bugs, error/errors, defect/defects, flaw/flaws, glitch/glitches, delay/delays, failure/failures, crash/crashes**. Observation scales the head score by **-0.8**, not by the descriptor **1.15** factor; additional internal `no` or odd external negation scales by **-0.7**. Outside observations, descriptor composition uses **1.15**, with **-0.7** for explicit `no`. Contextual fallback scores never create standalone head aliases. **dont** is a negator only in a complete observation frame; **funcitonal** is accepted only as a descriptor there, not through general fuzzy matching. Unknown/fourth descriptors, punctuation, newlines, and conjunctions block recognition. See [the full curated lists and boundaries](HIGHLIGHTING_ALGORITHM.md#curated-noun-head-frames).

Other shared rules remain: additive “not only/just/merely/simply” and certainty “no/without doubt” exceptions; listed bugs/errors/problems/delays absence via “without” or “free of/from”; support/reliability lack via “lack of” or “lacks”; **-0.7** absence/lack reversal before **-0.7** odd external negation, with emotion removed on reversal; **0.65/1.15** less/more scaling for listed positive qualities. Context-only aliases reuse existing lexeme scores, not invented standalone noun meanings. Legacy positive-term/negative-head composition uses the listed head's score × **1.15**. See [exact lists, scopes, and scoring precedence](HIGHLIGHTING_ALGORITHM.md#3-adjust-the-evidence-using-nearby-context).

At the default **0.30** importance threshold and **0.50** correctness cutoff, **“dont see any functional problems”** is one full-span **positive green** highlight: score **+1.36**, importance **0.34**, heuristic correctness **0.64**, null calibrated confidence, no emotion. “Don't see no functional problems” yields negative evidence **-0.952**; “don't think there are no problems” yields **-0.833** and its “no functional problems” variant **-0.95795**. All three stay uncolored at default importance, rather than falsely green; [source regressions](../tests/noun-context.test.ts) cover these cases.

Bounded `if`/`unless`/`would`/`could` and hedges, **couldn't/wouldn't/shouldn't** observation prefixes, questions, plus narrowly listed “too ADJECTIVE to ACTION” and negated “QUALITY enough” frames, set heuristic correctness to **0.44**, preserving lexical/negation polarity rather than inventing arbitrary reversals. They normally fail the shared **0.50** minimum correctness filter: lowering sensitivity's importance threshold alone cannot expose them. For example, “If I dont see any functional problems.” and “I dont see any functional problems?” keep score **+1.36** and importance **0.34**, but abstain at defaults. The analyzer retains withheld clause/aspect evidence, but the current Manual panel lists explanations only for displayed highlights (plus overall sentiment and target count). Exact dictionary phrases retain their authored internal reading before external rules apply.

Aspect metadata can share a copular predicate across at most **three explicit `and`-coordinated subjects**, each up to **three noun tokens**, within **18 tokens** before `is`/`are`/`was`/`were`. Listed opinion verbs prefer a following explicit object, not the preceding subject. This remains a noun-proximity heuristic with no pronoun resolution or semantic parser; it does not change highlight colors.

## Build and install

1. Install dependencies with `npm install` (PowerShell: `npm.cmd install`).
2. Run `npm run build:extension`. This first builds the shared library, then creates **extension-dist/**.
3. In Chrome/Edge → Extensions, enable **Developer mode**, choose **Load unpacked**, and select **extension-dist/**.
4. Pin textheat to the toolbar and click its icon on an ordinary HTTP/HTTPS page.
5. After source changes, rebuild and click **Reload** on the extension card; reload test tabs to replace old content scripts.

The build is local, bundled and MV3 CSP-compatible. No npm publication is required. For the website download, run `npm run demo:build`: it builds the extension, packages and validates the actual downloadable ZIP at **demo/public/downloads/textheat-chrome.zip**, then builds the website with that ZIP at **demo-dist/downloads/textheat-chrome.zip** (served as **/downloads/textheat-chrome.zip**). Extract the downloaded ZIP and select the extracted folder with **Load unpacked**. No store publishing is performed automatically.

## Off / Auto / Manual

- **Off** (default): no text analysis or expensive observers. Previously generated highlights are removed without a page reload. Global mode applies to accessible open tabs.
- **Auto**: progressively processes readable text as it approaches the viewport. Auto asks for optional HTTP/HTTPS website access through a user gesture in the popup. It registers the content script only on permitted hosts. Existing accessible pages are updated as well.
  - The first permission dialog may close the popup. A short-lived background intent completes the selected Auto mode when full requested host access is granted, without requiring a second click. Denial, a newer explicit mode selection, or expiry after two minutes cancels the intent; unrelated permission grants do not enable Auto. Already-granted access uses the normal direct save path.
- **Manual**: no automatic page processing until you choose a tool. The popup shows your actual browser shortcut assignments, not assumed keys.
  - **Toggle whole page:** default `Alt+Shift+H`. Starts/stops progressive page highlighting; “whole page” includes distant content when scrolled into view, not an eager body rewrite.
  - **Click to check text:** default `Alt+Shift+C`. Click a readable text block to open a local analysis panel. Escape cancels. Links, buttons and editable controls keep their normal behavior.
  - **Check selected text:** default `Alt+Shift+S`. Select ordinary page text, then use the shortcut or popup button. The analysis panel provides text, polarity, importance and explanations without changing the selected page content.
  - **Clear page highlights:** removes highlights and stops processing this page.

Configure shortcuts in your browser's Extensions → Keyboard shortcuts. Browser/OS conflicts may leave shortcuts unassigned; the popup reports that. Mode and appearance settings are global; disabling the current site overrides them. Manual whole-page on/off state is ephemeral for that tab and document, not stored browsing history.

## Settings

**Emoji reactions** is a separate, default-Off presentation option in both the popup and Settings. On a highlight's first visible reveal, matching emojis burst outward for **1,600 ms** while the retained emoji simultaneously scales from zero to full size over **360 ms**. The four particles have horizontal end offsets of **−18, −6, +6, +18 px**, rise to **−24/−34 px** at 40% of the burst (half the horizontal end offset), and end another **8 px** higher (**−32/−42 px**). The badge remains slightly above and to the right of the upper-right edge. Emotion takes priority: joy 😊 (with 🎉 burst particles), anger 😠, sadness 😢, fear 😰, surprise 😮; otherwise positive 👍 or negative 👎. Reactions are decorative, not additional analysis or confidence.

Enabling reactions on already-visible highlights attaches static badges instead of starting a page-wide burst; waiting/animating highlights and accepted reveal requests retain first-burst eligibility. Appearance-only updates while reactions and animation remain enabled preserve ongoing bursts and queued requests, without replaying settled bursts or consuming new targets. Explicit static presentation cancels that target's queued/active burst without replay. Disabling animations or requesting OS reduced motion clears the queue and settles active reactions as static; missing animation APIs also deliberately use static reactions. Emoji motion always honors the OS even if the separate highlight reduced-motion preference is disabled. Disabling reactions, Off, Clear, and teardown remove the overlay and cancel pending effects. Resetting a target cancels its request/effect and permits a genuinely new reveal.

Reactions live in a separate inert, screen-reader-hidden, pointer-free shadow overlay, never inside highlighted text or editor content. Original text, copy/selection, form values, and highlight counts are unchanged. Positions follow scrolling/resizing without changing line wrapping; offscreen/removed anchors are recycled. Limits are **128 visible reaction badges**, **128 pending target references**, **128 deferred overflow references**, **eight simultaneous bursts**, and **four particles per burst (32 maximum)**. Accepted visible requests drain in request order as slots finish or are canceled; idle static badges may be recycled to make room. Offscreen requested reveals retain eligibility in the same bounded queue, create no host/layer while offscreen, and start on their first visible refresh/scroll even if highlight observation has already ended. Offscreen requests do not block visible requests. Removed/ineligible targets are pruned. When the pending queue is full, newest requests are held in the bounded deferral queue rather than dropped or consumed: as slots free up, later scroll/refresh passes promote them back into the pending queue and retry them automatically. Only overflow past the deferral bound is rejected, and it is still not consumed, so a later explicit reveal may retry it. Deliberate static cancellation consumes accepted, pending, and deferred requests alike, without later bursts. This is a decorative opt-in: on dense or overlapping text some reactions can crowd one another; disable it if distracting. Manual analysis panels and native fields do not get burst decorations.

Popup: sensitivity (the shared importance threshold), adaptive/default/dark/high-contrast/custom theme, animation, **Rounded corners** (Off/sharp by default), explanations on hover, **Include code blocks**, **Include editable text**, and current-site enable/disable. The edge preference is saved with the other local settings and also available on the Settings page. Both inclusion toggles default Off. Settings additionally exposes reduced-motion preference, viewport preload distance, debug logging, custom six-digit-hex JSON palette and hostname overrides. Site thresholds can be set/reset in Settings. The website keeps sharp edges regardless of the extension preference.

The radius preference also styles extension-owned in-page UI (manual panel, pick hint, reaction badges and highlighted-span corners). It does not round page-provided website controls or change sentiment colors. Popup/options mirror the saved choice immediately; existing highlights update in place.

While the popup is open, the page status refreshes about twice per second from the main-frame controller. Highlights count current connected page highlight spans, not cumulative analyzed words or highlights in the separate Manual panel. Newly analyzed content increases the count; removed/cleared content decreases it. Processed counts text-node analysis jobs and is a separate metric. Sampling stops when the popup closes and does not inject scripts, trigger analysis, persist counts, or contact a server.

**Editable-text opt-in:** rich `contenteditable` and document design-mode editors can receive inline highlights. Cursor/selection offsets are preserved during wrapping/restoration; DOM work within an editor is paused during IME composition and resumes afterward. Native text/search/email/url/tel inputs and textareas are **Manual analysis sources only**, because they cannot contain inline highlight spans. Click-to-check reads their value without changing it; Check selection reads selected native-field text when the browser exposes selection offsets. Passwords, disabled fields, and unsupported control types remain excluded even with opt-in. No draft text is stored or transmitted. Reactive editors and undo history may still interact with inserted spans: disable this option if editing is affected. Real-browser behavior is certified by the Playwright harness in `browser-tests/` (real Chromium, real built bundle): selection offsets survive wrapping, DOM work pauses during a real IME composition and resumes after it, and Ctrl+Z after wrapping is a no-op in Chrome because the programmatic wrap invalidates the typing undo entry (text is never corrupted). Real Gmail/Facebook editors, whose frameworks mediate input and undo, still require manual testing; regression mocks are not certification.

**Adaptive is the default palette.** It derives highlight colors from the surrounding page surfaces, including light and dark areas on the same page. Each opaque adaptive highlight foreground/background pair has at least **4.5:1 contrast**; this is a guarantee within that pair, not an accessibility certification of the surrounding website or custom palettes. The extension refreshes adaptive colors after page class/style changes and OS color-scheme changes. Images and gradients use a solid-color fallback rather than attempting to infer their pixel colors.

Preferences and explicit hostname overrides are saved only in this browser profile's local extension storage (`chrome.storage.local`), not synchronized with a browser account. Existing local settings remain usable. Old synchronized settings are **not automatically read or migrated**; users who previously relied on sync may need to reconfigure their preferences and site overrides in each browser profile.

Default word highlights introduce **no extra tab stops** or ARIA name duplication. Optional basic hover explanations use the browser's native `title` tooltip; keyboard users can use the explicit Manual analysis panel for full explanations. Native tooltips have browser-controlled styling/placement rather than a custom popup tooltip at every word. The panel has a close button and Escape dismissal. Reduced-motion CSS always removes transitions when requested by the OS; the setting also controls whether JavaScript skips animation setup.

## Architecture and DOM safety

- Public imports from `textheat` / `textheat/browser` reuse exact core analysis. Build bundles that package locally. Settings do not reinterpret sentiment or confidence.
- Text nodes are discovered incrementally with TreeWalker, then direct parent targets are observed with IntersectionObserver (**default 0px preload**, so processing starts at the viewport). Highlights animate once when they enter actual visibility. Previously saved explicit preload values are preserved; set Preload distance to 0 in Settings if upgrading from an earlier default.
- Small idle/time-sliced queues bound traversal and work; one job failure leaves the original text unchanged. Single text nodes above 24,000 UTF-16 units are deliberately left unchanged to avoid monopolizing the main thread.
- MutationObserver batches new content and text/visibility changes. Body replacements and framework-rendered replacement nodes are rediscovered without monkey-patching history or frameworks. Unchanged nodes are cached using weak state. Observer targets removed from the document are unobserved.
- Individual text nodes become an owned `display:contents` wrapper with safe spans/text nodes. Surrounding elements, links, attributes, listeners and form state remain. Styling is scoped and has no font-size/padding/margin changes.
- Disabling disconnects observers, cancels work and animations, and restores original text-node identity if the page hasn't edited the wrapper. If a page has edited generated content, cleanup preserves the current text/children instead of restoring stale input.
- No HTML-like page text is parsed as markup. Manual analysis uses DOM `textContent` and the shared safe DOM renderer.

## Permissions and privacy

- `storage`: global settings and explicit hostname overrides, read and written only through `chrome.storage.local`. The extension does not access `chrome.storage.sync`. **No page text, analysis output or browsing history is stored.** Hostname overrides only exist when configured by the user and stay local to this browser profile.
- `activeTab`: temporary access to the current tab for an explicit Manual tool.
- `scripting`: local bundled script/style injection and progressive Auto registration.
- Optional `http://*/*`, `https://*/*`: Auto across permitted websites. Off stops processing and unregisters automatic scripts but does not revoke already granted permissions. Revoke host access in browser extension settings.

All extension analysis runs locally in memory. No telemetry or analytics, text transmission, external requests, remote JavaScript, eval, or remote inference: page text, visited URLs and analysis results are not sent to a server, and saved preferences/hostnames are not sent to browser-account sync by the extension. Protected pages (browser settings, web stores, other extensions), PDF viewers, file URLs and pages where access is denied cannot be processed. The popup reports unavailable access gracefully.

## Limitations

- Main-frame ordinary DOM only. Iframes and shadow-root text are not traversed in this baseline; closed roots and cross-origin frames are never bypassed.
- Page highlighting is **rendered per text node**, but analysis merges the inline text of each block container: adjacent text nodes are joined in document order and analyzed as one string, split only at nested block elements and existing wrappers and capped at 128 nodes and 24,000 characters per group. Longest phrases, curated noun-head/negated-observation frames, eight-token context windows, absence/lack frames, and coordinated targets therefore survive inline element splits such as `<p>not <em>bad</em></p>`; predictions are mapped back to per-node spans for rendering, and element structure is never rewritten. A block also inherits its previous sibling block's trailing text (up to 200 characters) as analysis-only context, so negation, hypothetical, comparison, or target context split across a sibling block boundary still composes; the carried context itself is never highlighted, and highlights render only in the block that owns them. Context does not cross into nested blocks or across different parents, and blocks processed out of document order fall back to per-block analysis. Manual panels analyze their explicitly collected input as a separate text string, not a semantic reconstruction of the page.
- POS/aspect/sentiment semantics retain the shared English lexical baseline's ambiguity and vocabulary limitations. Unknown alphabetic words are candidate nouns, pronouns are not resolved, and sarcasm, implicit sentiment, unfamiliar expressions, quotations, and complex grammar can be misinterpreted. No evidence/highlight is not proof of neutral meaning; a larger authored dictionary is not an accuracy guarantee.
- Some highly reactive frameworks or styles can still interact with inserted inline spans. Editable regions and code are excluded unless separately opted in. Native controls are never rewritten; allowed text fields support opted-in Manual analysis only. Passwords, SVG/math, hidden/inert content, and extension UI remain excluded. Reversibility and tests reduce risk but do not guarantee compatibility with every site.
- No extension-store or Firefox certification is claimed. Chrome API usage is isolated to the extension application layer; Firefox would require manifest/API compatibility adaptation.

## Test

The release checklist in [EXTENSION_RELEASE_CHECKLIST.md](EXTENSION_RELEASE_CHECKLIST.md) separates automated checks from the real-browser installation, permissions, and store-submission steps that still need manual verification.

Run `npm run test:extension`, `npm test`, `npm run typecheck`, and `npm run build:extension`. For focused source-only privacy regression checks without rebuilding, run `npx vitest run tests/extension/storage.test.ts tests/extension/background.test.ts`. Tests cover visibility, once-only animation, dynamic updates, SPA body replacement, thresholds/themes, safe text, parent/text-node preservation, links/forms, copy selection, Manual tools, exclusions, cleanup, reduced motion and permission contracts. UI/service-worker tests exercise mode switching, permission denial, shortcuts and settings under mocked extension APIs. Storage tests verify local settings/site roundtrips, ignoring old sync settings, no sync reads/writes, and local-only change handling; background tests cover serialized local read-modify-write updates and validation.

Start `npm run dev` and visit **/extension-test-page.html** for the local lifecycle fixture. It includes long-page scrolling, dynamic insertion, hidden/expandable content, links, lists, table, code, forms, editable text, Unicode and HTML-looking text. Select a Harness mode to test the exact shared controller without installing; leave **Harness Off** when testing the installed extension to avoid two independent controllers.

Automated mocked browser APIs do not prove actual toolbar installation. Follow the load-unpacked steps above for browser permission-dialog and shortcut validation. The fixture separately verifies real DOM observers, scroll behavior and cleanup in a browser.
